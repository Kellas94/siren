## Job feasibility and the remaining startup race

Windows provides the required Job APIs; the inspected OS build supports nested Jobs. API availability is not demonstrated assignment in Electron's utility-process environment. Existing enclosing Jobs, token/session restrictions and UI limits can make assignment fail. Such failure must refuse shell creation; do not enable breakaway or fall back to PID-tree termination. Assignment needs actual process handles with set-quota/terminate rights. [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject).

**Host ownership:** main creates an unnamed, non-inheritable root Job; sets kill-on-last-handle-close without breakaway/silent-breakaway; starts a utility host with PTY spawn denied; opens and retains the actual host process handle and validates identity; assigns it to the Job; verifies membership; only then releases its private spawn gate. Main alone retains the root Job handle. Neither renderer nor child receives a Job name/handle, and disposal/GC must not close it during Lock. Main death closes the last handle and terminates members; normal Stop-All terminates that owned Job. A native wait on the held host handle terminates the root Job when the host dies, independent of main's JS progress. [Job lifetime/inheritance](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

Host assignment before PTY permission covers later ordinary descendants, but utilityProcess starts running before main can assign it. The exact pre-adoption utility startup/helper interval must be inspected and qualified. Already-created children are not retroactively assigned. Electron's JS utilityProcess API does not expose Windows process-creation Job attributes. Assigning the entire main process to this terminal Job would change ownership of SIREN/other windows and make Stop-All terminate the app; it is not an equivalent fix. No root-job crash guarantee is claimed before this interval is resolved for the exact launch path.

**Session ownership:** a fresh nested session Job must belong below the host Job. A shell that inherits the host chain can then be explicitly assigned to its empty session Job; future children inherit both. Non-breakaway inheritance covers detached-console/CreateProcess descendants, while session termination leaves sibling sessions running. Keep real shell handles and immutable creation identities; PID alone, console-list notifications and journals are not authority. A native root-handle monitor terminates the remaining session Job on natural shell exit. [Nested hierarchy rules](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs).

The inspected exact node-pty 1.1.0 `src/win/conpty.cc:385–433` uses one startup attribute, `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`, and `CreateProcessW` with `EXTENDED_STARTUPINFO_PRESENT | CREATE_UNICODE_ENVIRONMENT`. It has neither `CREATE_SUSPENDED` nor `PROC_THREAD_ATTRIBUTE_JOB_LIST`. It returns the PID after the shell is already running. Therefore `adoptSession()` called after `pty.spawn()` can miss early children: they inherit the host Job but not the later session Job. `-NoProfile` and withholding the first input lease do not prevent shell/module/native startup from creating children. Terminating the host Job would kill all sessions and cannot satisfy per-session Stop.

The strongest native creation primitive for this gap is an **atomic ordered Job list at CreateProcess**, alongside the ConPTY attribute, so the shell is a session member before executing. It requires a reviewed native spawn integration (for example a patch to the pinned node-pty ConPTY path) and new source/build/artifact qualification. A suspended-create/assign/resume patch leaves its own crash-before-adoption orphan interval unless creation already inherits an appropriate kill guard. A separate bootstrap broker would alter the chosen architecture and also needs explicit design/evidence. A standalone main-only addon cannot inject the missing attributes into an unchanged node-pty call. No upstream patch, broker or alternative has been implemented or selected here. [Windows Job-list process attribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

**Handles and verified cleanup:** native waits/monitors operate on retained handles, not JS timers. Per-session Stop closes input, terminates the session Job, waits within the specified 10,000 ms deadline and queries authoritative Job accounting; Stop-All does the corresponding host operation. A termination call's success is not an exit receipt. Completion-port messages aid diagnostics but are not guaranteed, and their PIDs can be reused. Handle waits plus accounting, with appropriate release of exited process references, must establish zero remaining owned processes; failed/unknown query or deadline returns cleanup failure. Register monitors before releasing a spawn gate and define monitor teardown so host/main/root loss races cannot double-close handles. [TerminateJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject), [Job accounting](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information), [completion notification limitations](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_associate_completion_port).

The candidate's helpers/conhost paths need explicit ownership classification and qualification too. OS-inbox ConPTY does not establish that every system/helper process is a session member. No broad conhost/PowerShell/Node kill is acceptable. Retaining non-inheritable root handles is critical: a duplicated root handle in a surviving child would defeat the intended last-handle owner-death trigger. Temporary session-handle duplication needed by atomic spawn must be scoped, closed and covered by the separately main-owned root lifetime. Jobs provide application lifetime management, not a security sandbox against arbitrary privileged OS actions.
