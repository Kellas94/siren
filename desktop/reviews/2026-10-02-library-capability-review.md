# SIREN library capability assessment

Author: `/root/review_pending_work`. Requested 2026-10-02; completed 2026-10-03, Europe/Bucharest. Read-only assessment of the portable development source and current primary upstream documentation. This is a recommendation report, not release admission, a performance qualification, or an implementation plan. No product files, installed artifacts, existing reports, dependency lockfiles, or dependencies were changed.

**The most useful additions are TanStack Virtual for the Docs register and MiniSearch for richer workspace search. Keep Lezer for the current Code scope; investigate reuse of its existing incremental API before replacing the parser. Reuse and profile Mermaid/ELK before adding another diagram engine. Defer Tree-sitter and Pyodide until a specific language or execution capability justifies their additional assets and maintenance.** These priorities are engineering judgments grounded in the source below; speed improvements have not been measured with the proposed libraries.

## Current implementation

**Docs.** [R78.html:66367](C:/Claude/SIREN_WORK/portable/desktop/baseline/R78.html:66367) sets `MAX_WORKPAPERS = Infinity`; documents have a 300-block bound. [renderWorkpaperList:69690](C:/Claude/SIREN_WORK/portable/desktop/baseline/R78.html:69690) filters the complete document array, replaces the list children, and builds a button for every matching document. Rows can include variable-height approval, drift, agent and comment metadata. This is full-list rendering, with no viewport window or overscan. It captures/restores focus and sets `aria-current`; those behaviors matter when choosing a virtualizer.

[renderWorkpaperBlocks:71744](C:/Claude/SIREN_WORK/portable/desktop/baseline/R78.html:71744) similarly rebuilds every block in the active document, including insertion controls and open discussion/diff panels. Some large source controls already use deferred hydration. It would be inaccurate to describe every large source value as eagerly painted. Virtualizing the editable body is substantially harder than the register: exact Find, selection, contenteditable controls, heading navigation, comments and focus currently depend on real DOM elements.

**Search.** Docs register search caches a flattened lowercase string in a WeakMap, scans it with `includes`, and debounces list rendering by 120 ms ([69570](C:/Claude/SIREN_WORK/portable/desktop/baseline/R78.html:69570)). `touchWorkpaper` invalidates that cache ([68712](C:/Claude/SIREN_WORK/portable/desktop/baseline/R78.html:68712)). These optimizations already exist.

Workspace search is different: the input directly calls `runWorkspaceSearch` ([26895](C:/Claude/SIREN_WORK/portable/desktop/baseline/R78.html:26895)). Each query scans diagram source lines, metadata and comments; Docs titles, block digests and comments; and the resolved Code catalog including private drafts and released copies ([38539](C:/Claude/SIREN_WORK/portable/desktop/baseline/R78.html:38539)). Results use literal lowercase substring matching. The scan counts all hits but renders only the first 300. This avoids an unlimited result DOM, but does not bound the scan or rank matches. Separate Docs Find and Code Find retain exact source/DOM offsets; they should remain distinct from a relevance index.

**Code.** Local package manifests independently confirm MIT packages `@lezer/common` 1.5.3, `@lezer/lr` 1.4.10, `@lezer/highlight` 1.2.5 and `@lezer/python` 1.1.19. The Python grammar has SIREN corrections; it is not stock upstream. The existing inventory records empty class patterns, parenthesized with-items and form-feed indentation changes. [analyseCode:109906](C:/Claude/SIREN_WORK/portable/desktop/baseline/R78.html:109906) normalizes parser input, projects ranges onto the original source, and calls `SirenPythonParser.parse(parsed)` without reuse fragments. [getCodeSyntaxTokens:109920](C:/Claude/SIREN_WORK/portable/desktop/baseline/R78.html:109920) parses again for highlighting. Analysis limits are 100,000 characters, 3,000 lines and 120 structural nodes; an alternative parser alone does not change that product contract.

**Diagrams.** SIREN already carries Mermaid 12.0.0 and an embedded `@mermaid-js/layout-elk` 0.1.7 bundle. [ensureElkLayout:39785](C:/Claude/SIREN_WORK/portable/desktop/baseline/R78.html:39785) registers the embedded loaders; Standard/Dagre and ELK are existing choices. Rendering already uses request IDs to reject obsolete results ([35633](C:/Claude/SIREN_WORK/portable/desktop/baseline/R78.html:35633)). Custom SVG lanes and badges add work beyond graph layout. A Promise-returning layout call is not proof that its CPU work runs in a real worker. Vendor text contains worker support and fallback implementations; I did not establish the active constructor/worker identity at runtime.

## Recommended priority and practical boundaries

**1. TanStack Virtual: strongest targeted fluidity candidate for the Docs register.** Its headless core supplies viewport ranges, overscan, size measurement and scroll positioning, with stable item keys ([installation](https://tanstack.com/virtual/latest/docs/installation), [API](https://tanstack.com/virtual/latest/docs/api/virtualizer)). The concrete opportunity is reducing list DOM and reconstruction to visible rows plus overscan. It will not make the preceding full-array filter free, nor cure large editable-source input latency. Persistent document IDs, variable row measurement, focused offscreen rows, `aria-current`, keyboard travel, search/filter scroll restoration and independent Docs windows are the integration cost. There is no evidence here that a small register needs virtualization. Recommend evaluating it for large registers; defer editable-body virtualization until selection/Find behavior is explicitly qualified. This prioritization is inferred from the current full-list loop, not a measured speedup.

**2. MiniSearch: strongest new capability candidate.** It supports ranking, field boosts, prefix/fuzzy matching and suggestions ([official documentation](https://lucaong.github.io/minisearch/)). That improves discovery when a user remembers an approximate title, owner or phrase. It changes search semantics: token matching is not arbitrary substring matching, and code identifiers, punctuation and Romanian/Unicode text need deliberate tokenization. Preserve literal Find/Replace and a clear exact-search option. Index results must retain diagram, document, block, source and draft IDs so current navigation still lands on the right object. Use existing block digests and resolved Code catalog boundaries; do not index raw HTML/JSON or accidentally widen private-draft scope. A disposable per-workspace index avoids making an index another authoritative project format. Imports, undo/redo, merges, releases, draft changes and project replacement all require invalidation. Large knowledge text adds index memory and cold-start work. Faster repeat queries are plausible, but unmeasured; a debounce or digest cache for the existing global scan is also a lower-dependency option.

**3. Retain Lezer and existing layout infrastructure.** Lezer already supports `TreeFragment.addTree/applyChanges` and incremental parsing ([reference](https://lezer.codemirror.net/docs/ref/)). Sharing a parsed tree between highlighting and structure analysis, or reusing changed ranges, is more directly related to the observed duplicate parse than changing libraries. Normalized CRLF/raw offsets, grammar corrections, tabs, Unicode, edits and multiple private windows must still remain correct; incremental reuse is not guaranteed to help every edit. The separate CodeMirror native assessment owns editor conclusions. Historical long-native-input latency T256 remains open; this report does not attribute it to Lezer or claim a parser replacement fixes it.

ELK already supports real workers when configured, and worker termination ([upstream README](https://github.com/kieler/elkjs)). First distinguish layout CPU, SVG construction, custom decoration and export work before choosing a new layout dependency. An actual worker can move layout computation off the UI thread; DOM measurement and SVG painting still remain. Existing latest-request guards should be preserved. Any dependency refresh needs the exact engine resolution/license and wrapper-peer compatibility addressed. No new layout library is recommended merely for fluidity.

**4. Tree-sitter only for a demonstrated language-analysis expansion.** It offers incremental trees and separate language grammars, but requires parser initialization and language-WASM loading. Its upstream documentation warns that older WASM dynamic-linking formats can fail even with a supported parser ABI ([web binding README](https://raw.githubusercontent.com/tree-sitter/tree-sitter/v0.27.0/lib/binding_web/README.md)). Moving SIREN requires a new structure/range adapter, explicit incomplete-source behavior and independent raw-offset tests; a new grammar does not supply CPython compiler equivalence. Current corrected Lezer coverage is useful migration evidence, not proof of Tree-sitter equivalence. No tested improvement over Lezer was established here.

**5. Pyodide only if CPython-backed diagnostics or deliberate Python execution becomes a product requirement.** A compiler-backed `ast.parse` service could add syntax fidelity without running the imported source; startup, memory, AST coupling and resource limits would still require measurement. It is excessive solely for syntax colors or structural maps. Current docs require a module-type worker and explain that main-thread Python computation blocks UI ([worker guide](https://pyodide.org/en/stable/usage/webworker.html)). A worker separates computation from the UI; it is not evidence of security containment or a resolution of G-6/G-14. Optional Python packages, host interop and any future execution would need a separate capability design. No execution or containment claim is made here.

## Desktop packaging and maintenance implications

[renderer.mjs:216](C:/Claude/SIREN_WORK/portable/desktop/build/renderer.mjs:216) generates hash-bound inline scripts, `default-src 'none'`, `worker-src blob:`, and `connect-src 'self' blob:`. It does not permit CDN scripts or `wasm-unsafe-eval`. [main.mjs:219](C:/Claude/SIREN_WORK/portable/desktop/src/main.mjs:219) enables sandbox/context isolation and disables Node integration. Pure-JS core/search modules fit the existing offline bundling model more closely than a WASM runtime. Tree-sitter/Pyodide cannot be assumed to load unchanged under this policy; they need an explicitly qualified local asset and WASM/worker strategy. This is a source-policy inference, not a performed CSP loading test, and is not a recommendation to broadly relax CSP.

For each chosen library, the maintenance cost includes exact asset/lock pins, notices, provenance, regression controls and updates—not just its direct dependency count. TanStack's release history includes scroll-anchor fixes; MiniSearch's changelog documents search/index behavior changes ([TanStack release](https://github.com/TanStack/virtual/releases/tag/@tanstack%2Fvirtual-core@3.17.11), [MiniSearch changelog](https://github.com/lucaong/minisearch/blob/master/CHANGELOG.md)). These are reasons to qualify upgrades against SIREN's behavior, not to follow every upstream release automatically. Existing desktop dependency documentation explicitly leaves the complete renderer/runtime SBOM and redistribution qualification unfinished. This assessment records licenses and costs; it does not certify redistribution compliance.

The recommendation is therefore selective: viewport virtualization where DOM size is the cause, indexed relevance where richer discovery is the goal, and reuse/profiling of the parser and layout libraries SIREN already carries. Product implementation and measured benefit remain outside this completed read-only review.
