# Windows PIN keystore persistence — pinned upstream research

Author: `/root/media_batch_review` (Codex subagent). Date: 2026-10-07.

Scope: read-only inspection of SIREN account call sites, the retained other-author six-profile matrix, and primary Electron/Chromium/Microsoft sources. No product, test, generated asset, profile, or PIN modification; no GUI, process termination, native experiment, CI, or release approval performed by this author. This is research and a correction-boundary proposal, not verification of a fix.

## Result

The pinned Windows implementation has a real dependency between encrypted records and a separately persisted Chromium profile key. The public Electron `safeStorage` operations examined do not expose an acknowledgment that this profile key has been successfully persisted. Changing only synchronous calls to asynchronous calls does not remove that dependency. There is an internal preference write barrier, but its ordinary completion callback alone does not establish successful publication, and it is not exposed as a supported application JavaScript Local State flush API.

Per-record, current-user Windows DPAPI is a feasible direction for removing the extra Chromium Local State key dependency. It still depends on Windows credentials/profile state and requires actual restart qualification. None of this establishes the cause of the user's original incident or recovers an already lost key.

## Exact Windows call paths

### Synchronous record encryption and profile-key initialization

The [Electron safeStorage binding](https://raw.githubusercontent.com/electron/electron/v44.5.1/shell/browser/api/electron_api_safe_storage.cc), especially lines 185–255, checks application readiness/availability and calls `OSCrypt::EncryptString` or `DecryptString`; returning the encrypted buffer does not call a preference commit. Its asynchronous queue uses `OSCryptAsync::GetInstance` and an `Encryptor`, likewise without a preference persistence acknowledgment.

The exact synchronous Windows source is **restored by an Electron patch**, because this Chromium revision removed the upstream sync backend. The [pinned patch list](https://raw.githubusercontent.com/electron/electron/v44.5.1/patches/chromium/.patches) includes `revert_oscrypt_remove_sync_backend.patch`; therefore historical Chromium sync files alone would be an incorrect version basis.

In that [restoration patch](https://raw.githubusercontent.com/electron/electron/v44.5.1/patches/chromium/revert_oscrypt_remove_sync_backend.patch), Windows `os_crypt_win.cc` starts at patch line 6119. `Init` (6372–6398) loads an existing key or generates a random 32-byte key when missing/decryption fails. `EncryptAndStoreKey` (6238–6250) DPAPI-protects that key, adds a `DPAPI` header, Base64-encodes it and calls `PrefService::SetString("os_crypt.encrypted_key", ...)`. `Init` then sets the in-memory key and returns. Normal record encryption (6320–6342) uses AES-256-GCM with this key and a `v10` envelope. There is no commit in those routines. A newly generated key after restart cannot decrypt ciphertext produced with a different earlier random key; this is a source-level mechanism, not a capture of either live key in the matrix.

### Local State ownership, startup, shutdown, and asynchronous provider

[BrowserProcessImpl](https://raw.githubusercontent.com/electron/electron/v44.5.1/shell/browser/browser_process_impl.cc), lines 134–166, creates a `JsonPrefStore` at `DIR_SESSION_DATA/Local State`, reads it, and builds `local_state_`. Its shutdown hook (187–191) calls `local_state_->CommitPendingWrite()`. `CreateOSCryptAsync` (442–451) constructs Windows `DPAPIKeyProvider(local_state())`, explicitly relying on prior synchronous `OSCrypt::Init`. The [main-parts startup](https://raw.githubusercontent.com/electron/electron/v44.5.1/shell/browser/electron_browser_main_parts.cc), lines 710–723, calls that initialization before creating the main message loop; its shutdown path calls the browser-process hook.

The [pinned DPAPIKeyProvider](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.130/components/os_crypt/async/browser/dpapi_key_provider.cc), lines 60–97, reads the same `os_crypt.encrypted_key` preference, validates Base64/header, calls `CryptUnprotectData`, and expects a 32-byte AES-GCM key. It does not establish a separate Windows keystore independent of Local State. Missing preference is permanently unavailable for this provider; DPAPI decryption failure is classified temporarily unavailable.

The [pinned safeStorage documentation](https://raw.githubusercontent.com/electron/electron/v44.5.1/docs/api/safe-storage.md) recommends async APIs for nonblocking work, key rotation, and availability handling. `isAsyncEncryptionAvailable()` resolves after asynchronous initialization; `encryptStringAsync()` resolves with encrypted bytes; `decryptStringAsync()` returns `{result, shouldReEncrypt}`. None is documented as a disk durability barrier. Retain these semantics when considering migration; neither availability nor same-process roundtrip proves crash survival.

## Persistence boundary and non-solutions

[JsonPrefStore](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.130/components/prefs/json_pref_store.cc) schedules writes on preference changes (305–313, 489–496). `CommitPendingWrite` (274–298) starts scheduled work and queues callbacks behind the file task runner's pending operations. Those callbacks carry no success result. Separate next-write/next-successful-write hooks (324–385) distinguish successful writes and may wait for a later success. Therefore a wrapper must handle failure and bounded completion explicitly; simply exposing the ordinary callback as “key persisted” would overstate it.

[ImportantFileWriter implementation](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.130/base/files/important_file_writer.cc) uses a default ten-second commit interval and creates, writes, flushes, then replaces a temporary file (43, 245–327). The [Windows File::Flush implementation](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.130/base/files/file_win.cc), lines 478–486, calls `FlushFileBuffers`. However, the [ImportantFileWriter contract](https://raw.githubusercontent.com/chromium/chromium/152.0.7977.130/base/files/important_file_writer.h), lines 25–35, distinguishes protection against application crashes during writing from system crashes: it explicitly does not specify whether the old or new version survives a system crash, and does not eliminate integrity/recovery requirements. The ten-second interval explains a possible window; sleeping ten seconds is not a success acknowledgment or a fix.

The inspected [app binding](https://raw.githubusercontent.com/electron/electron/v44.5.1/shell/browser/api/electron_api_app.cc) has no `CommitPendingWrite` binding. No supported public JavaScript Local State durability barrier was found in these pinned `app`/`safeStorage` surfaces. `session.flushStorageData()` is documented for [unwritten DOMStorage](https://raw.githubusercontent.com/electron/electron/v44.5.1/docs/api/session.md), and its [implementation](https://raw.githubusercontent.com/electron/electron/v44.5.1/shell/browser/api/electron_api_session.cc), lines 699–701, calls the browser context's storage partition `Flush()`, not browser-process `local_state_`. It is unsuitable as the missing acknowledgment. OS-level power-loss guarantees were not established in this research.

## Feasible correction directions and proving work

1. **Current-user DPAPI per record, through a small native main-process backend.** Protect the serialized PIN verifier/credential record directly and atomically persist the resulting blob using SIREN's owned storage boundary. This removes the application's Chromium-generated AES key and its Local State dependency. Use a bounded, versioned envelope and a narrowly scoped native binding/helper; do not place secrets in shell arguments, logs, or renderer IPC. Keep ciphertext ownership, atomic publication, readback, error reporting, and Lock sequencing explicit. This is a design direction, not an implemented or tested solution.

   Microsoft's [CryptProtectData contract](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) returns an encrypted blob with integrity protection, normally tied to the current user's credentials and computer. `CRYPTPROTECT_LOCAL_MACHINE` broadens decryption to other users on that machine, so it is inappropriate for preserving current-user protection. [CryptUnprotectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptunprotectdata) remains dependent on the corresponding Windows context/entropy. This route avoids **Chromium** profile-key persistence, not Windows profile/master-key dependence or cross-machine portability constraints. A successful API return still does not persist SIREN's output file by itself.

2. **A maintained Electron/native integration for explicit Local State publication.** A custom Electron patch/upstream API could force the owned preference writer, observe real write success/failure, and read back the expected protected-key identity before accepting a dependent record. This is internal C++ integration, not an existing supported JavaScript call or an ordinary addon with documented access to Electron's private global `PrefService`. It brings Electron maintenance and upstream API work. Its success contract must remain limited to qualified application-termination behavior unless stronger system-crash behavior is separately proved. Do not edit native `Local State` JSON from application JavaScript.

For either route, keep existing record bytes and version dispatch. Migrate a legacy safeStorage record only after genuine successful decryption and validation, then guarded atomic replacement with readback; never convert decryption failure into automatic PIN reset, plaintext fallback, or a new silently accepted verifier. Missing earlier profile-key material is not reconstructible from a stored AES ciphertext by either proposed migration. Preserve blocked records for diagnosis/recovery.

Required proof before calling either direction a correction: fresh owned profiles, immediate forced termination after the first accepted setup, setup→Lock→kill, repeated restarts, existing graceful controls, exact executable/data-root/record identity, real decrypt and record validation on restart, rejected wrong PIN, corruption/truncation, unavailable Windows protection, cancellation/Lock during writes, failed atomic publication, and interrupted migration with the old record retained. Observe persisted files and outcomes without a timing-altering pre-encryption canary. These process-termination tests still do not claim power-loss qualification. Keep the original adverse matrix immutable.

## Limits

The exact pinned sources establish the storage architecture and absence of a public acknowledgment in the examined APIs. They support a concrete deferred-key-persistence hypothesis for the retained matrix, but no live in-memory key capture, failing-key comparison, or controlled correction experiment was performed here. Exact `pref_service.cc/.h` retrieval through the web reader failed; the successful barrier analysis uses the pinned `JsonPrefStore` implementation and Electron's actual caller, and does not invent an uninspected forwarding implementation. No maximum availability, portable-machine recovery, native UI behavior, packaged release, or independent approval is asserted.
