## Recommended next coherent batch

**Diagram types and starters: a compact catalogue plus “Create new diagram”.** Restore discoverability and genuine creation together, preserving the diagram currently being read or edited. Offer the frozen built-in starters/templates through a native-owned finite catalogue. Selecting a card only displays its bounded literal source and capability description; an explicit creation command creates a separate diagram and opens its genuine working view. Browsing must never replace current source, apply styles, save pending fields or copy private source metadata into the new object.

This is a useful finite functional batch. Custom-template storage/deletion and durable layout preference are separate contracts and should not be smuggled into it by copying the legacy application closure. Layout discovery can identify existing direction controls and explain source-controlled engine selection now; a later engine-choice batch should prove rendering/provenance/export semantics before presenting an operative picker.

## Finite implementation boundaries and concrete seams

1. **Catalogue contract/build seam:** add a self-contained immutable data catalogue with allowlisted IDs, group/title, exact starter source, truthful native capability notes and provenance to the frozen baseline. Use a hash-checked build-time data extraction or explicitly reviewed literal data; no legacy startup, localStorage, network/icon fetching or evaluation of imported user source. Keep 19 named starters plus9 built-in examples as a finite upper catalogue, with Advanced represented only as help for direct source. Unknown IDs refuse. Proposed bounds: ≤32 entries, title≤160 UTF-16 units, description≤512, each source≤8KiB UTF-8 and≤200 lines, total catalogue≤128KiB. Verify exact existing examples fit before adopting these bounds; these are proposed limits, not measured sizes in this report.
2. **Controller/UI seam:** one compact Types & templates disclosure near the source/Build controls, not another permanent toolbar row. Use textContent/select options and a readonly literal source preview, at most20 entries per displayed page, no eager render of every template. Maintain existing preview size expectation. `src/ui/windows/diagram.js` must retain source/Guided/Build/Style/Inspector pending state and focus/selection while browsing. Preserve local history/version and presentation edits; clear private retained preview and fence late callbacks on pause/dispose/changed admission. New creates a separate view only after success. An unavailable creation grant leaves browsing usable with an honest message.
3. **Main creation seam:** implement a finite owner request accepting catalogue ID, bounded optional name and operation ID, not arbitrary project JSON/sourceRefs/renderer-supplied existing ID. Resolve the selected project and capability through actual sender/frame/context membership, check access epoch and current selection again after I/O, allocate the new ID in main, and append exactly one new Diagram to the latest source-aware manifest. Preserve all old entities, opaque fields, sources, imported view/style and existing ordering. Retain conflict/idempotency semantics so double-click/unknown completion cannot create duplicates. `src/windows/domain.mjs`, existing project store/manifest transaction owner, IPC/preload and native view admission are the seams; an existing edit grant must not silently become unrestricted project creation. 4. **No incidental style inheritance:** a new catalogue diagram starts from its own exact source and deliberate minimal metadata. It must not inherit the active diagram's title, nodeMetadata, presentation, sourceRef or font/colour overrides. Catalogue business examples are examples, not approval/compliance facts.

## Layout choice: useful but a separate rendering contract

Direction is already available for admitted flowcharts in Build. Engine choice is different: baseline `state.layoutEngine` is a legacy preference, not evidence that imported native `diagram.layout` is a safe place to write a string. Native domain preserves broad imported layout/view objects, while current draft/style ownership is deliberately narrower. Do not overwrite those objects or add a property the shared export path ignores.

Before adding a native engine selector, choose and label its authority: saved per-diagram choice shared by preview/export/Presenter, or explicitly temporary **Preview layout**. The latter must leave saved SVG export unchanged and communicate that limited scope. A saved choice requires one finite managed value, owner validation, undo/reset absence semantics and consistent render adapters; that is larger than catalogue discovery.

Source-owned init/frontmatter configuration has precedence. An engine picker must disclose or disable conflicts rather than silently stripping/replacing source configuration. Preserve original theme/font/colour provenance in `style.js` / `build/diagram-style.mjs`; selecting layout must not add theme defaults that override imported styling. Only report ELK active after actual loader and render success. On failure retain the source and last valid rendering, report refusal/fallback truthfully, and do not leave a picker displaying an engine that was never applied. Do not alter secure/maxEdges/htmlLabels policy.
