## Authority distinctions to preserve

1. **A descriptive fileId fallback is not language authority.** `selectedSourceDisplayName` currently returns the first safe name matching either the exact sourceRef or standalone provenance.fileId. An earlier row with a matching fileId but a different sourceId can therefore win before a later exact-ref row. Do not copy that first-match OR rule into Python eligibility. Prefer exact admitted sourceId/version/SHA claims; provenance.fileId and filename extensions remain descriptive. Add an ordering case containing both the stale fileId row and the genuine exact-ref row. Multiple conflicting exact claims must yield unknown rather than first-wins Python.

2. **Ordinary Save source advances working identity without advancing the project manifest.** `invokeSourceMutation` explicitly keeps Save separate from Docs/project-manifest mutation; `NativeWorkingSources` advances references from real owner receipts. A new v2 can be valid for a working Code window while selected sourceRefs/Docs remain pinned to v1. A metadata helper that requires v2 in the selected manifest would lose Python/name metadata immediately after a successful Save and could wrongly disable analysis. Root has chosen a narrow main-owned fallback: current genuine working grant, supplied ref equals actual `workingSources.referenceFor(grant)`, and a same-source selected base. Borrow only language/displayName, never current-version document links. Reject cloned/foreign grants, stale refs and same-version/different-SHA conflicts. Mirror the existing guarded working-reference distinction in `homeWindowSummaries`.

3. **The catalogue's maximum selected version is not necessarily repository latest.** Its current source map groups selected manifest refs, while working admission may read a newer stored version. Use “selected/project version” when that is the actual authority. Do not call manifest v1 “latest saved” after an unlinked working v2 Save, or silently discover/update repository latest to make the label true.

4. **Docs-origin Python needs an explicit supported metadata route.** Migration can create a source from a Knowledge row with `fileType:'python'` and docs provenance, without any standalone codeFiles row. Existing `source-migration` and native source-bundle fixtures demonstrate this shape. Restricting language to codeFiles would downgrade those existing sources. Root has chosen bounded exact-ref Knowledge fileType claims alongside exact codeFiles.language claims, with python/text conflict producing unknown and no extension inference. Scan language claims before deduplicating relation rows: two rows in one document may disagree even when the relation itself is a single document/ref pair. The stored source filename is ordinarily Knowledge `row.name`; reading only `row.fileName` misses existing supported names. Sanitize supported aliases without exporting row bodies.

## Relationships, bounds and labels

- Match current document links by all three source reference fields. Classify an earlier association only when the same sourceId has a lower version and the exact reference is admitted. Same hash or same filename under another sourceId establishes no relation. Deduplicate relation counts by documentId plus exact ref, and keep separate exact/earlier counts and bounded previews. “Unlinked” must mean this selected version is unlinked; metadata scan incompleteness must remain unknown/truncated rather than an asserted absence. Release snapshots and recovery drafts are outside this discovery scope.
- Treat document agent ID/version as authored claims. Do not nominate one owner from multiple documents or infer runtime use/approval. Validate duplicate/invalid document IDs consistently, rather than accidentally merging unrelated rows by a reused ID.
- Bound work as well as output. The initial helper's per-describe scan over every association could produce roughly 4,096 catalogue rows × 16,384 scanned associations. Root is introducing an index by sourceId. Reuse one context per verified immutable snapshot for comparison candidates instead of parsing up to 64 MiB of metadata for each of up to 64 windows. Invalidate/recreate the cache for a new snapshot/project/epoch; do not reuse a context after in-place source membership mutation.
- Sanitize/cache the document caption and agent descriptor once per document, outside matching row loops. Repeatedly normalizing a long title for many rows multiplies work despite a finite row count. Keep finite input scans, per-string limits, per-source previews and aggregate payload bounds explicit. If the claim scan is truncated, a later unseen conflicting language claim must not be silently ruled out. Catalogue total/filter counts should describe the searchable bounded range truthfully.
- Keep array/reference/provenance reads descriptor-based where untrusted live objects can reach the pure helper. Test getters on sourceRefs entries, provenance, sourceRef fields and adapter outputs without executing them. JSON-parsed workspace metadata is a separate boundary from live outer objects; do not infer that all inputs are getter-free merely because one portion came from JSON.
- `NativeSourceAnalysis` already captures both genuine Code frames and binds B using windowId plus exact rightRef, then rechecks references during I/O/publication. Human-readable labels must decorate these captured identities, never replace them. Keep full version/hash Details, retain eligibility when a safe label is missing, and capture comparison labels with the request/result generation. A stale B label must not cause silent retargeting after peer Save/close/project change/Lock. Metadata callbacks must not bypass the existing final authority checks.
