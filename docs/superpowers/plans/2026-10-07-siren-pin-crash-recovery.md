## Candidate boundary and constraints

Direct per-record Windows DPAPI would avoid Chromium's generated key, but the separate C# prototype was blocked by actual Windows Code Integrity before execution. It has zero qualified cases. Do not change Windows policy, rename the binary to evade it, weaken encryption, reset PIN or reuse the qualified process reader for cryptography.

Evaluate an alternative using the existing Electron executable and supported safeStorage operations in a dedicated, owned protection profile. This is a separate architecture, not execution of the rejected binary. Before any protected PIN publication:

1. A fixed, bounded headless protection process encrypts the actual serialized verifier and exits gracefully. Do not show a UI or expose a renderer bridge.
2. A second process independently decrypts the exact returned ciphertext using the same dedicated profile and confirms equality in memory. Wait for both normal exits; a mere output buffer or availability result is insufficient.
3. Only then may the caller atomically publish/read back the versioned PIN record and acknowledge setup. The initial provider crash or failed receipt must publish no PIN.

Use separate protection and UI profiles; never run concurrent writers to the same protection profile. Keep operations serialized across the existing single-instance Data-root authority. No plaintext PIN digits go to the provider; the existing scrypt verifier remains in main-owned memory. Serialized protected payloads and ciphertext use private bounded pipes, never command arguments, environment variables, logs, renderer IPC or arbitrary files. Fixed encrypt/decrypt/verify operations accept no shell command, executable, network target or caller-selected record path. Runtime paths, profile ownership, process identity, byte budgets, deadlines, exits and cleanup must be verified. Reject unknown protocol/version or malformed/truncated frames.

This retains Chromium profile-key dependence but seeks a real independent-process recovery receipt before publication. It requires a prototype and actual application crash regression; it is not equivalent to native write-success proof, power-loss safety, same-Windows-user isolation or recovery after Windows-profile loss. Measure latency before choosing it.
